# 1.0.0 — release notes and verification record

The full reasoning, provenance and verification behind the 1.0.0 changes. This is
the long form that used to live in `CHANGELOG.md`; the changelog carries the
bullets, this carries the _why_ and the evidence.

Nothing here is required reading to use the library.

## [1.0.0] - 2026-11-01

First major release. The breaking changes are the end of ES5 output, deep
imports being closed off, test artifacts no longer being published, corrected
range algebra on empty ranges, and a constructor that rejects inverted ranges.
The third of those is the one most likely to affect you: `intersection()` no
longer returns `null` for a connected-but-empty result, which flips any
`=== null` test on it. See the table in the Breaking section. Everything else is
additive or tooling.

### Breaking

- **ES5 output dropped.** All build targets now compile to `es2020`. The
  `dist/esm5` build no longer exists and `package.json` `module` now points at
  `dist/esm`. Consumers still needing ES5 must transpile themselves or stay on
  0.1.x. This was forced by TypeScript 7 removing `target=ES5` (error TS5108),
  along with `baseUrl`, `moduleResolution=node10` and `downlevelIteration`.
- **`dist/karma` and `dist/spec-node` are no longer published.** They are test
  artifacts and were never part of the import surface.
- **Deep imports are no longer resolvable.** `require("range-ts/dist/cjs/index.js")`,
  `import "range-ts/dist/esm/index.js"` and similar paths now fail with
  `ERR_PACKAGE_PATH_NOT_EXPORTED`, because the package declares an `exports` map
  that exposes only `.` and `./package.json`. This was verified safe to do: every
  public name in the library (16 of 16) is already reachable from the package
  root, so a deep import could not obtain anything additional — it could only
  create a dependency on an internal _path_. The failure is loud and happens at
  the consumer's build time rather than silently. `range-ts/package.json` remains
  exported for tooling that reads the version.
  Before 1.0.0 there was no `exports` map, so anything under `dist/` was
  reachable by anyone who knew the layout.
- **Range algebra on empty ranges changed, including a `null` that is no longer
  `null`.** `encloses`, `isConnected`, `intersection` and `span` were computed
  with `contains`, which answers a question about the whole range; for an empty
  operand that returns false at both ends for reasons unrelated to the bound
  under test, so the answers were wrong. They are now computed from Guava's
  `Cut` ordering — the full reasoning is in the Fixed entry below. The fixes are
  correct, but they change return values on inputs that were always valid, and
  one of them flips a control-flow test:

  | call                                            | 0.1.8   | 1.0.0    |
  | ----------------------------------------------- | ------- | -------- |
  | `closedOpen(0,2).intersection(closedOpen(2,2))` | `null`  | `[2..2)` |
  | `closedOpen(0,2).isConnected(closedOpen(2,2))`  | `false` | `true`   |
  | `closedOpen(0,2).encloses(closedOpen(2,2))`     | `false` | `true`   |
  | `open(0,1).overlaps(open(0,1))`                 | `false` | `true`   |

  The last row is the bug that motivated the work: on 0.1.8 a range did not
  overlap itself.

  **What to check in your code:** any `=== null` or truthiness test on
  `intersection()`. It previously conflated two different facts. It now means
  only "not connected", and a connected-but-empty result comes back as a range
  object. If you meant "no overlap", test `.isEmpty()`, not `=== null`.

  **Scope, measured rather than estimated.** The shared API surface
  (`NumberRange`/`RangeMap`/`BoundType`) was fingerprinted on both versions
  across all 40 constructible ranges over 0..3 with all four bound-type
  combinations, every ordered pair — 1600 pairs across 6 methods, so 9600
  probes. 186 results changed. Every
  one of them involves an empty operand or a self-comparison of an open range.
  **Zero** changes on distinct non-empty pairs, and **zero** changes in the
  `true → false` direction: every difference is `false`/`null` becoming
  `true`/a value. Code that was correct on 0.1.8 for ordinary ranges is
  unaffected; what changed is what the library says about degenerate ones.

- **Constructing an inverted range now throws.** `new NumberRange(1, CLOSED, 0, OPEN)`,
  `NumberRange.closed(5, 1)`, `NumberRange.closedOpen(0.5, -0.5)` and any other
  range whose lower endpoint is greater than its upper endpoint raise instead of
  being built. 0.1.8 accepted them silently.

  The reason this is not merely untidy: an inverted range contains nothing, yet
  `isEmpty()` returns **false** for it, because `isEmpty()` asks "did the
  endpoints meet, with at least one side open" and an inverted range never met at
  all. Every guard this library builds on `isEmpty()` — the write-side guard in
  `RangeMap.combinedPut`, the read-side filters in `asMapOfRanges` and `span` —
  therefore lets it straight through, and `map.put(closedOpen(0.5, -0.5), 'x')`
  produced a map that reported `span() === [0.5..-0.5)` and one visible entry in
  `asMapOfRanges()` for a map associating a value with nothing. That is a hole
  through the empty-range invariant by the one input the invariant was written to
  catch everything else with, and it is invisible to exactly the checks that exist
  to stop empty ranges causing it.

  **What to check in your code:** any place a range is built from endpoints that
  come from outside — user input, a parsed file, a subtraction that can go
  negative. If it could be inverted, it used to be constructible and is now not.
  That is the intended outcome: the alternative was a range that lies about being
  empty.

  The rule is on endpoint **values**, not on cut positions, and that distinction
  is deliberate. Cut order puts an open lower bound above an open upper bound at
  the same value — which is what makes `(v..v)` empty-but-valid — so a validity
  check written on cuts would reject `(3..3)` along with the genuine inversions.
  All four equal-endpoint combinations remain constructible. Unordered endpoints
  (`NaN`) do not throw either: `NaN > 0` is false, so the documented non-answer
  keeps propagating as a negative rather than becoming a construction error.

  Not a regression — 0.1.8 behaved identically — but 1.0.0 is the release that
  made "empty associates with nothing" a stated rule, so the hole is closed here
  rather than left standing.

### Added

- **Generic `Scalar<T>` support.** `Range<T>` and `RangeMap<T, P, R>` now work over
  any exact scalar type (BigInt, custom decimal/decimal.js wrappers) rather than
  being tied to JS `number`, without the library depending on any of them.
  - Infinity is an explicit value each scalar owns. There is no "absent means
    unbounded" convention, and `null` and `undefined` are never conflated.
  - Checks are directional (`isPlusInfinity` / `isMinusInfinity`); there is no
    single `isInfinity()` that could merge the two.
  - `number` keeps its native `±Infinity` and is not given the synthetic sentinel
    treatment — replacing a native capability would change behaviour for no gain.
- **Three test environments**: `npm run test:node`, `test:jsdom`, `test:chrome`.
  `npm test` runs all three.
- **Mutation testing** via Stryker (command runner over compiled CJS).
- **Supply-chain hardening** in `.npmrc`: `min-release-age=7` (refuse package
  versions published less than 7 days ago) and `ignore-scripts=true` (never run
  dependency lifecycle scripts). Verified against a clean `npm ci` + full build.
- **`exports` map** with `types` / `import` / `require` conditions, so Node ESM
  consumers get the real ESM build instead of falling back to CommonJS interop
  through `main`. Verified: `import.meta.resolve('range-ts')` now returns
  `dist/esm/index.js` where it previously resolved to `dist/cjs`.
- **`sideEffects: false`**, so bundlers can drop unused exports. This is asserted
  from evidence rather than assumed: all eight source files were checked for
  top-level side effects and none exist.
- **`dist/esm` is now loadable by Node's ESM loader.** It previously emitted
  extensionless relative imports (`export * from "./core/bound-type"`), which
  bundlers resolve but Node cannot, so the ESM build was bundler-only. A new
  `scripts/finalize-dist.mjs` build step adds explicit `.js` extensions and
  writes `{"type":"module"}` / `{"type":"commonjs"}` markers into `dist/esm`
  and `dist/cjs` so Node declares the module type instead of reparsing to guess
  (which emitted `MODULE_TYPELESS_PACKAGE_JSON`).
  The fix is deliberately in the build, not the source: the sources stay plain
  extensionless TypeScript and the target-specific shape is produced by the
  compile step. `finalize-dist.mjs` re-scans after rewriting and fails the build
  if any extensionless specifier survives, because a scripted replace that
  silently matched nothing would otherwise ship an ESM build Node still cannot
  load.
- **`src/karma.conf.ts`** replaces `src/karma.conf.js`. Karma 6 loads its config
  with a plain `require()` and TypeScript 7 removed the JS API
  (`transpileModule`, `createProgram`) that `ts-node` hooks, so runtime TS config
  loading is unavailable on this toolchain; the config compiles via
  `tsconfig.karmaconf.json` to `dist/karma-conf/karma.conf.js` and Karma runs
  that. All paths in it are anchored to the repo root rather than to the file,
  since the runnable copy sits in `dist/karma-conf/` and a `__dirname`-relative
  path written as if it were in `src/` would silently land coverage reports one
  level wrong. `karma.conf.ts` is excluded from the library builds so it cannot
  leak into the published bundles.

### Changed

- TypeScript 5 → 7; `cjs`/`esm`/`karma` targets `es5`/`es2015` → `es2020`.
- CI pins Node 26 via `actions/setup-node`, so the lockfile no longer depends on
  whichever npm the runner happens to ship. Actions bumped: `checkout` v2 → v7,
  `setup-node` → v7, CodeQL v1 → v4.
- `test:chrome` now compiles its own target and refuses to report success over a
  zero-spec run (previously a missing `dist/karma/test.js` produced
  `TOTAL: 0 SUCCESS`).

### Fixed

- **`encloses`, `isConnected`, `intersection` and `span` now compare _cuts_, not
  containment.** _(Cross-listed under **Breaking** above: the old answers were
  wrong, but they were observable, and one of them was a `null` that consumers
  may be branching on.)_ They were written with `contains`, which answers a question about
  the whole range — so for an EMPTY range it comes back false at both ends for
  reasons that have nothing to do with the bound under test, and a range that
  plainly contains the empty one reported that it did not. The four methods are
  now decided on Guava's `Cut` ordering, where a bound's position depends on both
  its open/closed type and whether it is a lower or an upper bound
  (lower `CLOSED(v)`→`(v,0)`, lower `OPEN(v)`→`(v,1)`, upper `CLOSED(v)`→`(v,1)`,
  upper `OPEN(v)`→`(v,0)`). Concretely:
  - `[3..6]` now encloses the empty `[4..4)` (it always should have; Guava's own
    javadoc lists this case).
  - `(3..6]` still does _not_ enclose `[3..6]` — an open lower cut sits above a
    closed one, which `contains` could not express either way.
  - `[0..2)` is now connected to the empty `[2..2)`, and their intersection is
    that empty range rather than `null`. `null` means "not connected", which is a
    different fact from "connected with no overlap".
    Verified against a reference implementation of Guava's `Cut` model over all
    1296 ordered range pairs (values 0..3, all four bound-type combinations,
    empties included): 0 divergences on all five methods.
- **Writing an empty range into a `RangeMap` no longer moves the span of a range
  no listing shows.** The entry was stored, and `asMapOfRanges` /
  `asMapOfValues` filtered it out while `span` did not — so `put([0..1), 'a')`
  followed by `put([100..100), 'b')` reported a span of `[0..100)` for a map
  that visibly held one entry. Fixed at the write side (`combinedPut` now no-ops
  on an empty range, matching Guava and matching what `remove` already did), so
  no reader has to remember to filter and no future reader inherits the trap.
  `remove(empty)` is likewise a no-op that strands nothing.
- **`subRangeMap` no longer drops the parent's equality function.** It built the
  submap with `new RangeMap()`, so `putCoalescing` on a submap decided "same
  value" by `===` while the map it came from used whatever the owner supplied.
  The README's own shape — a `RangeMap<string[]>` built with lodash `isEqual` and
  written back through `subRangeMap` — coalesced correctly on the parent and
  silently stopped coalescing as soon as the write went through a submap. `eq`
  is now forwarded on every construction path, including the empty-submap path.
- **Comparing ranges built over different scalars now throws instead of returning
  a wrong answer dressed as a negative one.** `comparableScalar.compare(10, 10n)`
  is `NaN`, so `NumberRange.closed(0, 10).contains(10n)` was `false` and the
  same propagation made a `bigint` endpoint read as outside a range whose own
  endpoint it equals. Where two ranges' scalars are different objects _and_ the
  comparison comes back unordered, `encloses` / `isConnected` / `intersection` /
  `span` now throw with instructions to build both ranges from the same scalar.
  The guard is deliberately narrow: it fires on the unordered result only, so a
  same-scalar `NaN` (a documented non-answer) still propagates as `false`, and
  two scalars that _do_ order the values still compare normally. Note that the
  typed API already refuses most of these calls at compile time — `bigint` does
  not satisfy `Comparable` — so this guard is defence for plain-JS consumers and
  `any`-cast call sites rather than the primary barrier.
- **`tsconfig.*.tsbuildinfo` no longer ships.** Three of them were in the tarball
  (they were in 0.1.8 too). They are incremental-compiler state that a consumer
  cannot use, and they must stay on disk for `tsc -b` to be incremental, so they
  are excluded at pack time with `!**/*.tsbuildinfo` in `files` rather than
  deleted by the build. `.npmignore` was tried first and does nothing here — a
  `files` allowlist overrides it — so the exclusion lives in `files` itself.
  Tarball: 57 files → 54.
- **The README's `RangeMap` example did not run.** It called
  `Range.closedOpen(1, 5)`, but `Range` has no static constructors — the statics
  live on `NumberRange` (and on factories from `defineRange`). It also used
  `RangeMap` and `NumberRange` without importing them. Both corrected, and the
  example was executed against the packed artifact to confirm it now produces
  exactly the output its own `expect` asserts.
- **The published tarball is allowlisted; before 1.0.0 it was not.** There was no
  `files` allowlist, so npm shipped the entire repo minus `.gitignore`: `src/`,
  every tsconfig, and the `dist/karma` test artifacts. 0.1.8 published
  **81 files / 662 KiB unpacked** (`npm view range-ts@0.1.8 dist.fileCount
dist.unpackedSize`). 1.0.0 ships **54 files / 150 KiB** — `dist/cjs`,
  `dist/esm`, `dist/types`, README, LICENSE and CHANGELOG, and nothing else. Both
  figures are reproducible: the command above for the live 0.1.8,
  `npm pack --dry-run` for this tree.
- **The release workflow referenced a repository that does not exist**
  (`Github-Actions-Community/merge-release@main`): API 404 on every casing
  variant, `git ls-remote` falls through to a credentials prompt. Replaced with
  the plain `setup-node` registry-auth publish path, so there is no third-party
  action to audit and nothing floating on an unregistered org name.
- Removed `karma-typescript` / `karma-typescript-es6-transform` devDependencies:
  declared but never loaded (the Karma pipeline uses `karma-webpack`), and their
  `typescript@<=5` peer made them incompatible with TS 7.
- **`RangeMap`'s range-returning methods no longer break 0.1.8 consumers at the
  type level.** Going generic widened `getEntry`, `span`, `asMapOfRanges` and
  `asMapOfValues` from `NumberRange` to `Range<P>`, so unchanged 0.1.8 code
  like `const s: NumberRange = m.span()` stopped compiling with
  `'Range<any>' is missing the following properties from type 'NumberRange':
lowerEndpointValue, upperEndpointValue`. The runtime object was a
  `NumberRange` throughout — only the declaration had regressed. `RangeMap`
  now takes a third type parameter `R`, the concrete range class it accepts
  and hands back, defaulting to the new exported `DefaultRange<P>`:
  `NumberRange` for `Comparable` points, plain `Range<P>` otherwise. So
  `new RangeMap<string>()` is typed exactly as in 0.1.8, while
  `new RangeMap<string, BigIntPoint>()` still gets `Range<BigIntPoint>` with no
  extra annotation. The default is written `[P] extends [Comparable]` rather
  than `P extends Comparable` deliberately: the bare form distributes over a
  union point type, and `BigIntPoint` _is_ a union
  (`bigint | "+INF" | "-INF"`), which produced an unusable
  `Range<bigint> | Range<"+INF"> | Range<"-INF">` at every exact-domain call
  site.
- **The documented custom-scalar example violated its own contract, and the
  inverted-range check is what proved it.** The `Scalar<T>` interface requires
  `compare()` to order the domain's own infinities — "they are values of `T`
  like any other" — because an unbounded range is built by comparing them. The
  worked example in `scalar-range.spec.ts` (money as a decimal string) called its
  `asScaled()` helper straight through, so `M.all()` died with
  `SyntaxError: Cannot convert <<MIN>> to a BigInt`: the sentinel strings are not
  money and cannot be scaled. Nothing caught it before, because nothing in the old
  algebra compared the unbounded sides at construction time; adding the
  inverted-range check made `M.all()` throw at compile-to-test time on the first
  run. The example now orders its sentinels and asserts it directly.

  The general lesson is recorded in the example's comment: if a custom scalar ever
  trips the constructor check on an _unbounded_ range, the omission is almost
  always this one — `compare()` not handling the domain's own infinities.

- **`finalize-dist.mjs` resolved the dist path through `new URL(...).pathname`,
  which returns the percent-encoded form.** A checkout under a path containing a
  space or a non-ASCII character would have produced `%20/...`, every `existsSync`
  below it would miss, and the build would fail with "expected dist/esm to exist".
  Now uses `fileURLToPath`. Invisible on the maintainer's machine, which is
  exactly why it was worth fixing before publishing rather than after.
- **The release workflow's stage-id extraction no longer falls back to
  `rows[0]`.** If the name-and-version filter missed, the old code printed some
  other staged package's id and told the reader to `npm stage approve` it — an
  instruction that would publish the wrong artifact. A miss now reports no id and
  dumps the raw `npm stage list` output, which is honest instead of plausible.

## Security audit — the six invariant holes, in full

A full audit of this tree found **no remotely triggerable vulnerability and no
prototype-pollution path**. What it found was six ways to break an invariant the
library asserts about itself — each producing a silently wrong answer rather
than an error. All six are fixed and pinned by tests.

- **`Range` instances are frozen.** Every guarantee the constructor makes —
  bound types valid, endpoints not inverted, the scalar that ordered them — is
  undone by a field written afterwards, and `readonly` is compile-time only.
  Before: `NumberRange.closed(1, 10)` then `r.lowerEndpoint = 99` gave
  `[99..10]` with `isEmpty() === false`, the inverted-but-not-empty state the
  constructor itself refuses to build. Ranges are stored by reference and
  handed back by `getEntry` / `asMapOfRanges`, so a consumer mutating what it
  read corrupted the disjointness invariant `span` and `subRangeMap` rely on.
  Now `Object.freeze(this)` runs last in the constructor, the fields are
  `readonly`, and `Range.prototype` / `NumberRange.prototype` are frozen so
  `contains` cannot be rewritten process-wide.
  **Breaking** for subclasses that assign their own instance fields after
  `super()` — use prototype members, or pass everything through the `Range`
  constructor.
- **`comparableScalar` no longer orders non-numeric operands.** `<` / `>`
  coerce, and coerce _differently by type pair_: two strings compared
  lexicographically, a number against a string compared numerically. The
  comparator answered the same question differently depending on runtime type —
  `compare("9","10") = 1` while `compare(9,"10") = -1`. A comparator must be
  consistent: `intersection` / `span` merge bound types on `compare() === 0`
  and every sorted structure assumes the ordering holds. Non-numeric primitives
  now return `NaN` (unordered). bigint still orders against number, including
  past 2^53, because JS defines that ordering exactly. **Breaking** if you were
  relying on string coercion.
- **Bound types are validated at construction.** Every consumer asks
  `x === BoundType.OPEN ? … : …`, so any value that is not exactly `OPEN` is
  read as `CLOSED` — the permissive member, which _includes_ the endpoint. A
  TypeScript enum erases, so nothing checked a value arriving from JSON or a
  cast. Before: `new Range(1, "OPENN", 5, CLOSED, …)` constructed, `contains(1)`
  was `true`, and `toString()` rendered `[1..5]` so the log agreed with the
  wrong answer. `assertBoundType` now throws on anything but the two members,
  at the single choke point every `Range` passes through.
- **`likeRange` will not call a non-`Range` constructor.** It reflected
  `proto.constructor` and invoked it with four arguments the library had
  computed. Now bounded to `Range` and its subclasses.
- **`get` / `getEntry` are O(log n).** They were a linear `find` over the
  insertion-order array — ~500 µs per lookup at 10k entries, on the hot path of
  every consumer. Now a binary search over the **always-sorted** entry array.
  The comparison is cut-aware: "last entry whose lower endpoint does not exceed
  the key" is the wrong rule with a value-only `<=`, and that first version
  failed the existing open-boundary tests. Ties on lower value break CLOSED-first,
  matching cut algebra.
  - _Correction (2026-11-02)._ This entry originally read "a lazily built,
    write-invalidated sorted view". That was the first implementation and it was
    since removed — the lazy rebuild made every write O(n) because it had to
    re-sort, which is what the write-path rewrite below fixed. The array is kept
    sorted at all times; there is no view and no invalidation.
  - _Correction on the numbers._ Three different figures were circulating for
    the same two measurements: the CHANGELOG said `~400 µs → ~0.2 µs`, this
    file said `~500 µs → ~1–2 µs`. Re-measured on this tree against the built
    artifact: **40 000 lookups over a 40 000-entry map in 21 ms = ~0.53 µs per
    lookup.** Treat that as the current figure; the others are superseded, and
    the old-vs-new ratio is machine-dependent anyway.
- **CI token permissions made explicit.** `main.yml` and `codeql-analysis.yml`
  carried no `permissions:` key, so both inherited the repository default —
  historically "Read and write" — for jobs that write nothing.

Deliberately **not** changed, with reasons: `subRangeMap` returns values by
reference (documented — the map owns value identity, and copying would break
`putCoalescing`'s `eq`); `toString()` is a sink, not a sanitizer (documented);
the `Math.random()` sentinel in `remove()` compares by reference, so the random
id is decoration (commented as such).

### Measured cost of the freeze

`Object.freeze(this)` in the constructor is not free. Measured on this tree
(Node 26, 800k constructions, 3 interleaved rounds, same class with and
without the freeze call):

|          | avg per construction |
| -------- | -------------------- |
| frozen   | ~0.048 us            |
| unfrozen | ~0.018 us            |

**~2.6x, about 30 ns per range built.** Small in absolute terms — roughly
24 ms per million constructions — but it is a real cost on a hot path, paid
once per construction for a guarantee that holds for the life of the object.
Recorded here so the tradeoff is known rather than rediscovered.

### The one case that fails silently

TypeScript consumers who write to a range field get `TS2540: Cannot assign
to 'lowerEndpoint' because it is a read-only property` at compile time,
which is the good outcome. Plain-JS consumers running **sloppy mode** get no
diagnostic at all: `r.lowerEndpoint = 99` neither throws nor lands. The
value is unchanged and the object is frozen, so the guarantee holds — but
code that used to mutate now quietly does nothing instead of erroring.
Strict mode turns it into a thrown `TypeError`. There is no way to make the
sloppy-mode case throw without replacing the fields with throwing setters,
which would cost more than the freeze itself; documenting it is the cheaper
answer.

## The write path: O(n²) → O(log n + k), and why the data structure is not Guava's

### What was wrong

`combinedPut` walked the entire entry array on **every write** to bucket the
existing entries into "before / overlapping / after". A build of n puts is
therefore O(n²). Measured on the shipped code:

| entries | build time    |
| ------- | ------------- |
| 5 000   | 360 ms        |
| 10 000  | 1 188 ms      |
| 20 000  | 4 197 ms      |
| 40 000  | **15 027 ms** |

~3.5× per doubling. Every write path inherited it: `put`, `putCoalescing`,
and `remove` (which additionally did a sentinel put followed by a filter).

### The port, and the deliberate divergence

Guava's `TreeRangeMap` keys a `NavigableMap<Cut<K>, RangeMapEntry>` by lower
cut, so `putCoalescing` needs two lookups (`lowerEntry` + `floorEntry`) and
`remove` needs `lowerEntry` + `subMap().clear()`. It never scans. That is the
algorithm that was ported.

**The data structure deliberately was not.** A skip list or red-black tree
buys O(log n) insertion at the cost of pointer chasing, and in JavaScript
that cost is not amortised the way it is in Java:

- JS arrays are contiguous. `Array.prototype.splice` over a run is a native
  `memmove`, roughly **50× cheaper per element** than a JS-level scan.
- Prototyped both. 100 000 lookups: sorted array **19.6 ms**, skip list
  **56.7 ms**. The skip list's insertion advantage does not survive the
  pointer-chasing and per-node allocation in a JS heap.
- Reads dominate this structure. Blocking the cheap read to make the write
  asymptotically prettier would be the wrong trade for the actual usage.

So: sorted array, kept sorted at all times (no lazy rebuild), with two binary
searches to bound the overlapping window and one `splice` to rewrite it.
O(log n + k) per write.

Measured after the change, n=4000 → 8000:

| operation       | speedup |
| --------------- | ------- |
| `put`           | 118×    |
| `remove` (many) | 107×    |
| `putCoalescing` | 46×     |

### What the structure still is not

An interior `remove` splices in the middle of the backing array and memmoves
the tail. That is **O(n) per call, O(n²) for n interior removes** — O(n²) is
the honest theoretical value; the _measurement_ of it is not tight (see the
bench notes below). The port buys the constant (300–500× faster than the old
scan at every size: 10k 1 748 ms → 5.9 ms; 40k 30 339 ms → 90.9 ms), not the
exponent.

The guarantee to state plainly: **reads are O(log n); writes are O(n) worst
case with a native-memmove constant.** A workload dominated by interior
writes against a large map is where a different structure would win. It is
not this library's expected shape, and pretending otherwise in the gate would
be worse than saying it.

Confirmed by control experiment: removes that splice near the **end** of the
array stay ~linear (53.6 ms at n=80 000) while interior removes at the same
size cost 1 325 ms. Same code, same operation, different splice position.

## Guava equivalence: how it is actually checked

The README opens with "based on Guava's RangeMap". For most of this project's
life nothing verified that. The check now lives in the suite:

- `src/range-map/guava-ref.ts` — an independent model of `Cut` / `Range` /
  `TreeRangeMap`, transcribed from the Java source rather than from our
  reading of it. Plain-data ranges, linear scans instead of a tree: same
  logic, different machinery, so a shared bug in the two implementations is
  unlikely. Point-type-generic (`number` or `bigint`) so the same model can
  drive both domains below.
- `src/range-map/guava-differential.spec.ts` — 4 000 seeded trials × 6
  randomised operations over a continuous domain, run through both.
- `src/range-map/guava-differential-exact.spec.ts` — the same generator on
  a `bigint` **id** domain. See _Why a second domain_ below.

Three things are asserted, and the shape of each assertion is deliberate:

| assertion                         | why drawn this way                                                                                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Point mapping matches exactly** | `get(k)` over every k is the semantic contract of a range map. Zero tolerance.                                                                                                                              |
| **Never merges LESS than Guava**  | Structural divergence is allowed, but only one direction: every difference must show range-ts with fewer entries. A missed merge would mean a feature silently absent — the bug class this exists to catch. |
| **Throw behaviour matches**       | Neither side may accept what the other rejects.                                                                                                                                                             |

Current results, printed by the suites:

```
[guava-differential] ops=24000 structDiff=21 (over-merge=21, under-merge=0) emptyBridge=7/7
[guava-differential-exact] ops=18000 singlePoint=550 structDiff=48 (over-merge=48, under-merge=0) emptyBridge=10/10
```

Every structural difference is the documented over-merge. Zero under-merges.
All empty-range bridges fired, on both domains.

**Empty ranges are in the input space on purpose.** Guava treats an empty
`putCoalescing` as a bridge between two adjacent same-value ranges, and a
generator that excludes empty operands cannot see that path at all — which is
exactly how the gap stayed invisible for as long as it did.

### Why a second domain (bigint ids)

The numeric suite probes a continuous domain. A boundary that is wrong by
**exactly one point** is invisible there: between `[1..5]` and `[1..4]` the
probe at 4.5 cannot tell them apart, and the probes that could — the integers
— sit exactly where the OPEN/CLOSED decision is made, which is where a
continuous-domain test is weakest.

On an id domain the same failure is not a rounding error, it is one lost
record, silently, and the map still looks perfectly consistent around it. So
the exact suite probes **every id after every operation** — on an 8-value
domain full coverage is affordable, and partial coverage of an id domain is
the thing being tested. It also exercises the single-point write (`[n..n]`)
heavily (550 of 18 000 operations), which is the shape that strands or
swallows one id.

This is the domain the `bigintScalar` fixes in this release live on. An
unordered operand returning `0` made `closed(1n, 10n).contains("x")` true —
the kind of bug a spec-per-case misses and a whole-domain differential does
not.

### What the differential found that review did not

Running 0.1.8 (last published) against 1.0.0 on the same seeded sequences —
29 953 compared operations:

```
POINT-MAPPING regressions : 5     (all of them 1.0.0 being correct)
0.1.8 threw / 1.0.0 ok    : 0
1.0.0 threw / 0.1.8 ok    : 0
```

All five are one bug. In 0.1.8, `isConnected(X, X)` returned **false** when
`X` was fully open — only that shape; `[a..b]`, `[a..b)` and `(a..b]` were
fine. `combinedPut` used `isConnected` to decide which existing entries a
write affects, so a fully-open range did not connect to itself: the old entry
was never removed, the new one was appended, and `get` — a `find` in
insertion order — kept returning the **stale** value.

```ts
put(open(1, 2), "a");
put(open(1, 2), "b");
// 0.1.8: asMapOfRanges() has two entries; get(1.5) === "a"   <- write lost
// 1.0.0: one entry; get(1.5) === "b"
```

`remove(open(1, 2))` likewise left the entry in place. Silent write loss on
every fully-open range, for the entire life of the published package.

Worth stating explicitly because it changes the shape of the release: the
biggest correctness win in 1.0.0 was not the one being worked on. The
write-path rewrite was framed as a performance change and it was also a
correctness fix, and no amount of reading the old code surfaced it — only
running old against new on inputs nobody thought to hand-check did.

### Limits of this check

The reference model is a JS transcription of Java, not the JVM. It proves
range-ts matches Guava's **logic**. It cannot prove anything about Java-only
behaviour the model does not express, and it is only as faithful as the
transcription. Where the two disagree today the disagreement is known and
listed in the README's differences table rather than assumed to be our bug.

Three more limits, stated rather than left to be discovered:

- **Value-pattern diversity is bounded by the alphabet.** Four values over a
  five-point domain is a lot of patterns and not all of them. Widening the
  alphabet trades merge frequency for pattern count — with two values only
  2^_k_ distinct value patterns exist over _k_ writes, so most interleavings
  a real map sees were never generated; with four there are far more, but
  equal-value merges become rarer, so the absolute structDiff count falls
  (98 → 21) while the _harder_ cases become reachable. Read the ratio, not
  the raw count.
- **The exact-domain suite does not exercise the infinity sentinels.**
  `bigintScalar` supports `BIGINT_PLUS_INFINITY` / `BIGINT_MINUS_INFINITY`;
  the generator produces finite ids only. Unbounded ranges are covered by
  ordinary specs, not by this differential.
- **Over-merge is tolerated permanently, not tracked.** The one-directional
  structural assertion means a future change that merges _even more_ than the
  current documented difference passes silently. That is safe only because
  the point-mapping assertion is checked first and exactly — a merge across a
  gap, or one that swallows a differently-valued region, changes a `get`
  answer and is caught there. If the point-mapping assertion is ever weakened,
  this tolerance stops being safe.

## Benchmarking notes — five things this harness got wrong before it was right

The bench suite exists because "the suite got slower" is not actionable and
"put build is O(n²)" is. Getting it to produce stable numbers took three
separate discoveries, each of which had previously produced a confident
wrong answer.

**1. Setup must be outside the timed region.** `make(n)` builds the subject,
the timer starts after it. A first pass timed map construction inside the
`remove` measurement and reported the constructor, not the operation.

**2. `warmup: 1` measures unoptimised code.** On the remove-many scenario
at n=20 000, 25 consecutive rounds gave:

```
rounds  0- 9:   47 - 342 ms   (V8 still tiering up; wildly unstable)
rounds 10-24:   21 -  24 ms   (stable)
```

A 7–14× gap between warm and cold for identical work. With one warmup round
every sample came from the unstable band, which is how the harness reported
**O(n^2.92)** for code that measures O(n^1.1) once optimised. Warmup is now
14 rounds at the same size being measured.

**3. Median is the wrong statistic on a shared machine.** Every external
interference — scheduler, GC, a neighbour process, thermal throttle —
pushes a sample _slower_ and never faster, so the median absorbs
interference as signal. On a **pure-read** case with no allocation at all,
25 rounds:

```
n=20000   min 2.65   med 2.84   max 7.08   (2.68x spread)
n=40000   min 4.45   med 5.92   max 7.91   (1.78x spread)
```

Exponent from min: 0.75. From median: 1.06. The median version failed a
1.25 gate on some runs purely because seven samples caught a bad patch.
The harness now times with the **25th percentile** — the fastest honest run,
which reflects the code rather than the machine; p25 rather than strict min
so one anomalously cheap sample cannot set the number the way interference
sets the median.

**RETRACTION (2026-11-02).** The paragraph that used to sit here read:

> After all three fixes: four consecutive `bench:check` runs, zero failures,
> and the interior-remove case settles at O(n^2.03) instead of oscillating
> between 1.3 and 4.8.

It was wrong, and the way it was wrong is worth keeping. Three of the four
runs I made against that commit failed on **unchanged code** —
`putCoalescing (random order)` read anywhere between O(n^0.40) and
O(n^2.19). The three fixes listed above were real but **not actually in
effect**, and one more was needed:

1. **The runner overrode the warmup this file mandates.** `bench/run.mjs`
   passed `rounds: 5, warmup: 1` — precisely the configuration this page
   says samples the pre-optimisation band. `timeOp`'s default was 7/14 and
   nothing used it. Fixed: the runner now uses 7/14, both env-overridable
   (`BENCH_ROUNDS`, `BENCH_WARMUP`).
2. **The drift gate could never fire.** `Report.render` read
   `baseline[name]` while the writer nests rows under `measurements`, so
   every row showed `vs baseline  -` and `maxRatioVsBaseline` was inert.
   Fixed; the column now populates (0.97x–1.52x observed).
3. **Fixing warmup was not enough.** With warmup=14 the same case still read
   **1.48 / 1.96 / 2.25** on three consecutive runs, because small-n and
   large-n were timed in separate phases: a slow patch in one phase and a
   fast patch in the other multiply into the ratio instead of cancelling.

The fix that worked is **paired interleaved measurement**: time the two
sizes back to back as a pair, take the ratio _within_ the pair, alternate
the order per round so any systematic second-run effect cancels, and derive
the exponent from the p25 of those paired ratios rather than from a ratio
of two independently chosen quantiles.

After that the stable cases are genuinely tight (putCoalescing append
1.01–1.09, get hit 1.04–1.09, span 0.94–0.97).

**RETRACTION (2026-11-02).** The sentence that sat here — "three consecutive
`bench:check` runs, zero failures" — was a three-sample claim presented as
stability, and it did not hold. Re-measured on this tree with the current
runner (rounds=7, warmup=14), n=20000 → 40000:

| how the case is run            | interior-remove exponent     |
| ------------------------------ | ---------------------------- |
| this case alone, 12 runs       | min 0.57, med 0.85, max 2.01 |
| inside the full suite, 19 runs | spread **−0.19 … 3.53**      |

At the then-current **2.5** gate, the full-suite spread failed **2 of 19 runs
(~10%) on unchanged code**. The full-suite number is the one that matters,
because that is how the gate actually runs: eleven other scenarios ahead of it
move the heap and the thermal state, and warmup does not cancel that. The
earlier "wobbles 1.61 / 1.74 / 2.31" was again three samples.

Resolution: the interior-remove gate is raised to **4.0** — above the whole
observed spread, so it passes reliably. Its limit is stated rather than glossed:
at ±1.5 resolution this row guards against super-quadratic-by-2×, **not**
against a genuine cubic regression, which would land inside the noise. The
primary guard on that path is the baseline absolute-time ratio — which is
only a guard at all once note 4 below makes that ratio comparable.

`remove (wide chunks)` runs in ~0.035 ms, near the floor where an exponent is
not meaningful; one run read O(n^-1.08). That row is reported because the
harness prints every row, not because its exponent should be believed.

**4. Both gates were blind to their own calibration size.** The exponent
thresholds and the drift ratio are numbers tuned at n=20000, and nothing in
the runner checked that the run _was_ at n=20000. `BENCH_N=40000 npm run
bench:check` against the 20000 baseline reported four failures:

| measurement            | result               | why it is not a regression                  |
| ---------------------- | -------------------- | ------------------------------------------- |
| putCoalescing (append) | drift 3.2×           | twice the work                              |
| put (random)           | drift 3.0×           | twice the work                              |
| remove (interior cuts) | drift 3.4×           | twice the work                              |
| asMapOfRanges          | exponent 1.55 > 1.35 | a real wobble — but only at the larger size |

Three of the four are arithmetic: a drift ratio taken across two different
problem sizes measures the **size difference**, not the code. The fourth is
the interesting one — `asMapOfRanges` genuinely reads a worse exponent at
40k than at 20k, which means the 1.35 threshold is a statement about
n=20000 and about nothing else. Neither fact was recorded anywhere, so a
legitimate exploratory run produced four confident red lines.

Resolution: in check mode a size mismatch is a **configuration error** —
exit 2, nothing measured, caught in 0.1 s instead of after four minutes of
timing and then a lie. In report mode the run proceeds with a warning and
the drift column reads `n/a@20000`. Exploring at another size is fine;
presenting a cross-size ratio as drift is not.

The general form: **a threshold is a claim about the conditions it was
measured under.** Neither gate carried its conditions with it, so both
silently asserted them at sizes where they do not hold.

**5. "The exponent is machine-independent" was true only for single-class
workloads, and the gates were set as if it were universal.** The claim in this
harness's own header was that p "does not care whether the machine is fast or
slow… A linear operation reads p ~= 1.0 on a Xeon and on a laptop." For a
pure binary search that checks out — `get hit` read 1.02 on the dev box and
1.09 on the CI runner. For a **mixed** workload it is false, and
`put (random order)` is mixed: it interleaves CPU-bound JS work with a
memory-bandwidth-bound native `memmove`, so the measured exponent is a blend
of an O(n) part and an O(n²) part, and the blend weight is a property of the
machine's memory-to-CPU cost ratio rather than of the code.

| machine                        | `put (random order)` exponent |
| ------------------------------ | ----------------------------- |
| dev box (24-core, warm)        | 1.44 – 1.59                   |
| GitHub runner (2 vCPU, shared) | **1.77**                      |
| the gate at the time           | 1.75                          |

The gate sat between "new implementation ~1.4" and "old scan-and-rebuild
1.96–2.01" — a 0.5-wide window for a quantity with a ~0.3-wide cross-machine
spread. It fired on correct code, and the whole table came in 1.27×–2.02×
slow because the baseline had been recorded on a different machine entirely.

Underneath that is the harder point. A random-order build **is** quadratic:
each insert shifts ~n/2 entries, so the total is ~n²/4. The only reason it
reads 1.4 is that the native `memmove` is ~50× cheaper per element than the
JS scan it replaced. The difference between the good implementation and the
bad one is therefore a _constant_, and an exponent is blind to constants by
construction. **No threshold on that row could have separated them honestly.**

Fix, in two parts:

- Those rows gate at **2.05** — "must not exceed the declared class" — which
  is the only question an exponent can answer for them.
- The constant is guarded by **normalised drift**: the row's drift divided by
  the median drift of the rows marked `reference`, which are pure reads. The
  read rows are the fixed point precisely because a write-path change cannot
  touch them. Designating them matters: taking the median over _all_ rows
  would let a change that slows every write lift its own baseline and
  normalise itself away. The old scan-and-rebuild, ~15× in absolute terms,
  reads ~15n against that factor.
- And the gate itself is now tested with synthetic numbers
  (`bench/gate-selftest.mjs`), because a timing gate cannot be debugged on
  the machine that is misbehaving.

The general form, added to the one this section keeps re-teaching: **know
which axis your instrument actually measures.** The exponent measures class.
It does not measure constant, and on a mixed workload it does not measure
class stably either.

**A gate that fires at random trains people to ignore red.** Two of the cases
carry deliberately loose gates with the reason written next to them, because a
tight gate on an unreliable number is worse than an honest loose one. The
lesson this section keeps re-teaching is narrower and sharper than it looks: **a
three-run sample is not a distribution.** Both retractions on this page came
from writing down three numbers and describing them as the behaviour.

## Mutation survivors: proven equivalent, not ignored

After the rewrite, 15 mutants survived in the new write path. Rather than
assume, each was patched into a copy of the built CJS and searched for an
input that distinguishes it — 6 000 randomised
put/putCoalescing/remove sequences per mutant, then shrunk.

Two rounds of this were needed because the first was wrong twice over:
Stryker's column offsets are 1-based (slicing them directly shifted every
patch one character, producing undefined identifiers that _threw_, which
the harness counted as differences), and `firstLowerCutAtOrAfter` /
`firstLowerCutAfter` contain textually identical lines, so a first-match
replace patched the wrong function. Line-accurate patching was required.

**Killable (7)** — all in cut arithmetic, each now pinned by a spec carrying
the witness that kills it:

| line | mutant                              | why it matters                                          |
| ---- | ----------------------------------- | ------------------------------------------------------- |
| 67   | `c !== 0` → `true`                  | skipping the value comparison splits `[14..17)` wrongly |
| 67   | `c !== 0` → `false`                 | inverting it drops the surviving tail entry             |
| 67   | `c !== 0` → `c === 0`               | same witness as above                                   |
| 67   | `lowerCutSide(r) - side` → `+ side` | wrong sign swallows `(8..9]` into `[4..9]`              |
| 68   | `cut <= 0` → `true`                 | always-advance shatters a merged run into four          |
| 85   | `upperCutSide(r) - side` → `+ side` | wrong sign closes an upper bound that stays open        |
| 86   | `cut <= 0` → `cut < 0`              | strict form refuses an equal cut, leaves two entries    |

**Genuinely equivalent (8)** — no input over 6 000 sequences distinguishes
them, so a spec would be theatre:

- `start >= end && insert === null` (all three forms) — falling through with
  an empty replacement is a no-op splice.
- the two straddler comparisons (`< 0` → `<= 0`, `> 0` → `>= 0`) — the
  guard condition cannot be reached in the state the mutant would change.
- `!kept.isEmpty()` → `true` (both) — `kept` is provably non-empty whenever
  the branch is entered.
- `entries.splice(floor, 1)` → noop — the following `spliceOverlapping`
  covers and replaces that entry anyway.

Overall mutation score: **93.03%** (threshold 55), up from 91.80% before
this work, with 289 specs across Node, jsdom and Chrome.
